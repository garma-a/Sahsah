# Organise gameplay by feature with one host-action pipeline

Accepted 2026-11-11 in the backend restructuring grilling session (Q30–Q41). Keep gameplay in feature folders: catalog, rooms and lifecycle, games, realtime, media, preview and maintenance, with shared platform helpers. A shared host-action pipeline owns game locking, host checks, receipt recovery, roster/account locking, fresh time and idle expiry, status/version checks, handler execution, receipts and hints. Each host command has its own handler; starting a game uses named steps within its existing transaction. Layers and hexagonal architecture add indirection without a second implementation to justify it.

Use structured Pino logging with AsyncLocalStorage request context and explicit module/function scopes. HTTP requests, WebSocket connections and maintenance passes have correlation IDs; logs carry known operation, room, game and account IDs without bodies, credentials, signed media URLs, passcodes, invitation codes or phone numbers. Separate impossible-state invariants from business-rule checks: invariant failures log safely and roll back as INTERNAL_INVARIANT problems, while existing business statuses and codes remain unchanged.

Enable unchecked-index protection and derive database row/write types from Drizzle and request/response types from the existing Standard Schema contracts. Keep unavoidable assertions documented at validated or library boundaries. This makes feature changes local and catches invalid state assumptions during compilation while preserving routes, wire contracts, schema, transaction boundaries, lock order, idempotency and post-commit push behavior.
