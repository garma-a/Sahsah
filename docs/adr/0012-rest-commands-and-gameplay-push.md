# Use REST commands and push authorized gameplay updates

Accepted 2026-11-05 under API-Q3: the user delegated the delivery design to favor fast updates and low server load. Keep lobby/gameplay mutations in REST with durable retry identities, version checks and PostgreSQL transactions; use WebSockets to push the permitted game view after commit, with authorized REST snapshots for initial connection and recovery. Build the common projection once per relevant game version and audience instead of requiring every connected viewer to fetch it after every notification.

This refines the earlier hint-then-fetch fanout recommendation. Durable outbox records still contain only small routing/version hints; the dispatcher reloads current authoritative state and eligible recipients, coalesces superseded work and constructs transient host/viewer messages outside write locks. Viewer messages omit host capabilities and all question/forward audio URLs. An in-memory projection never replaces current membership/controller authorization; private URLs are issued only for permitted media and are absent from durable outbox/receipt payloads.

The trade-off is maintaining explicit projection schemas and revision-aware cache invalidation in exchange for fewer client HTTP round trips. A bounded cache/single-flight build may share safe projection data; it must not resurrect purged content or assume game version alone tracks terminal feedback, room changes or credential validity. Missed/duplicate/out-of-order updates recover through current snapshots; neither sockets nor the cache own accepted business state.

The 2026-11-05 engineering review selects Nest's native WsAdapter/`ws` for the small server-push protocol. Heartbeat scheduling, bounded authentication/subscriptions, reconnect backoff and slow-consumer recovery are explicit application responsibilities; no comparative capacity claim is made before tests.
