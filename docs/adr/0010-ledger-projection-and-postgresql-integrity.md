# Own the token balance through ledger inserts and verify financial transitions

Accepted technical refinement on 2026-11-03 under the user's request to improve the design. Q84–Q87 were explicitly accepted in the same review. Keep the 39-table model and the existing launch features. Staff remains Admin and Super Admin, with only staff management exclusive to Super Admin.

A service updating both a ledger and a balance gives every payment/game path two writes to coordinate. Instead, a ledger INSERT owns the balance change: a PostgreSQL trigger locks the account and adds the signed amount in the same transaction. New accounts start at zero; ledger history is append-only; direct balance edits are rejected. The nonnegative balance constraint rolls back an overspend. This is constant work per movement, without recomputing the account's full ledger history. Reconciliation may compare the full history separately. NestJS must never also increment/decrement the balance.

Use small named row checks and explicit financial observations on the existing payment inbox. Deferred PostgreSQL guards validate the final source/proof/settlement/credit together, while preserving an already accepted settlement when later refunds arrive. A native notification is not purchase proof, an inquiry is not unpaid closure unless it says so, and pending store purchases cannot fund a bank. Freeze order intent/digest, attributed owner, actual payment identity and accepted source. Native and Paymob projections cannot select older verification evidence. Cryptographic verification, provider amount normalization, authentication, pricing eligibility, full board validation and the game command engine remain NestJS responsibilities.

Companion SQL also enforces the accepted removal, voting, deletion and campaign boundaries. Deletion clearance becomes stale on new mapped funding, bank credit or native attribution; any staff review must cover that newer evidence. Exact forfeiture must commit with completed deletion. Campaign phone markers use a campaign-scoped keyed fingerprint until campaign end. Redaction preserves referenced identities without restoring erased personal payloads.

Trade-off: the schema now has PostgreSQL-specific behavior, so DBML export alone is insufficient. Load the exported schema, partial-index supplement and guards together in a reviewed migration; test them as one artifact. Keep private helper ownership/search paths and a restricted runtime database role. Do not put the complete game engine or a generic permission system in SQL. [Validation](../database/validation/README.md) uses disposable PostgreSQL 18 and reference transactions; it does not certify the future API or payment adapters.
